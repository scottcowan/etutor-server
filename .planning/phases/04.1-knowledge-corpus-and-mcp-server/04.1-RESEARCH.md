**Researched:** 2026-09-03
**Domain:** Layered content corpus (filesystem + frontmatter) and Python stdio MCP server
**Confidence:** MEDIUM-HIGH (stack verified against PyPI/slopcheck; MCP SDK API details are training-era knowledge — flagged where unverified)

## Summary

This phase has two halves: (1) a filesystem content corpus organized in L0→L3 layers under `docs/corpus/`, and (2) a Python stdio MCP server exposing 5 read-only query tools over that corpus. Neither half needs a database — the corpus is markdown + YAML frontmatter, indexed in memory at server startup, mirroring the existing pattern in `services/curriculum.py` (hardcoded Python list, no DB). All decisions about schema, directory layout, gating, and MCP tool signatures are already locked in CONTEXT.md (D-01 through D-21); this research focuses on the implementation mechanics Claude's Discretion leaves open: which MCP library, which frontmatter parser, how indexing/search work, how the server registers with Claude Code, how existing content migrates, and — critically — what a realistic v1 scope looks like against 975 curriculum topics (not "all curriculum topics" verbatim per CORPUS-01, which is materially larger than the CONTEXT.md decisions may have assumed).

**Primary recommendation:** Use the official `mcp` Python SDK's `FastMCP` class (bundled inside the `mcp` package as `mcp.server.fastmcp.FastMCP`, not the separate third-party `fastmcp` PyPI package) for the stdio server, `python-frontmatter` for YAML frontmatter parsing, plain substring/keyword matching (no `rapidfuzz`) for v1 search per D-14, and register the server via a project-local `.mcp.json` (not `.claude/settings.json`, which is a different, non-MCP config file). Scope the actual content-writing deliverable to a pilot subject (~10-15 topics) plus full infrastructure — writing L3 pages for all 975 topics is not achievable in one phase and CORPUS-01's "for all curriculum subjects" wording needs a scope note back to the planner.

### Pattern 1: In-memory index built once at process startup
**What:** On MCP server start, glob `docs/corpus/wiki/**/*.md`, parse each file's frontmatter with `python-frontmatter`, and build a small number of dicts keyed by `topic_id` / `slug` / tag. Rebuilding per-request is wasteful for a corpus of this size (hundreds of files at most); a stdio MCP server process is short-lived per session anyway, so a one-time startup scan is sufficient — no file-watching/hot-reload needed for v1.
**When to use:** Any read-heavy, low-write corpus where the filesystem is the source of truth and a DB would be over-engineering. Matches the existing precedent of `services/curriculum.py` (`CURRICULUM` is a module-level list built once at import time).
**Example:**
```python
# [ASSUMED — illustrative pattern, verify FastMCP decorator syntax against installed mcp 2.1.1]
import frontmatter
from pathlib import Path

CORPUS_ROOT = Path("docs/corpus/wiki")

def build_index() -> dict:
    index = {"topics": {}, "sources": {}, "experiments": {}, "people": {}}
    for md_file in CORPUS_ROOT.rglob("*.md"):
        if md_file.name == "index.md":
            continue
        post = frontmatter.load(md_file)
        bucket = md_file.parent.name  # "topics", "sources", etc.
        key = md_file.stem
        if bucket in index:
            index[bucket][key] = {"metadata": post.metadata, "content": post.content, "path": md_file}
    return index
```

### Pattern 2: Tool functions as plain Python functions, MCP registration as a thin wrapper
**What:** Write `get_topic()`, `search_corpus()`, etc. as ordinary, independently-testable Python functions that take the in-memory index (or a module-level singleton) plus arguments and return plain dicts/strings. Register them with `FastMCP` via decorator, but keep the decorated function a thin pass-through so pytest can call the undecorated logic directly.
**When to use:** Always, for MCP tool servers — decouples business logic from transport, which is also what the Test Patterns section below depends on.
**Example:**
```python
# [ASSUMED — illustrative, verify against mcp 2.1.1 FastMCP API before use]
from mcp.server.fastmcp import FastMCP

mcp_app = FastMCP("etutor-corpus")

def _get_topic_impl(topic_id: str, level: str | None = None) -> dict:
    entry = INDEX["topics"].get(topic_id)
    if not entry:
        return {"error": f"no corpus page for topic_id={topic_id}"}
    if level:
        # extract just the matching H2 section per D-03
        ...
    return entry

@mcp_app.tool()
def get_topic(topic_id: str, level: str | None = None) -> dict:
    return _get_topic_impl(topic_id, level)
```

### Anti-Patterns to Avoid
- **Rebuilding the index on every tool call:** wasteful and risks race conditions if files are being edited concurrently during authoring sessions. Build once at startup; if live-reload is needed later, add an explicit `reindex` tool rather than scanning per-call.
- **Putting business logic only inside `@mcp_app.tool()`-decorated closures:** makes unit testing require spinning up the stdio transport. Keep logic in plain functions (Pattern 2).
- **Treating `docs/corpus/wiki/index.md` as hand-maintained truth that can drift from the actual files on disk:** D-14 says the server builds its index from `index.md` AND the frontmatter of all L3 files — treat the filesystem scan as authoritative and use `index.md` as a human-readable table of contents only, not a second source of truth the server must reconcile with a scan. Recommend the server ignores `index.md` for indexing purposes and instead always globs the directories directly, then optionally regenerates `index.md` as an output artifact. (This is a discretion-area clarification for the planner — D-14's wording is slightly ambiguous about which of the two is authoritative.)

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Splitting `---\n<yaml>\n---\n<body>` markdown | A regex/string-split frontmatter parser | `python-frontmatter` | Edge cases (missing closing delimiter, YAML with embedded `---` in a string value, BOM handling) are already solved |
| stdio JSON-RPC framing for MCP | Manual `Content-Length` header parsing / raw stdin loop | `mcp` SDK's `FastMCP`/stdio transport | Official SDK; protocol version negotiation and error envelope format are non-trivial to get exactly spec-compliant by hand |
| Topic ID drift detection | Manually eyeballing filenames against curriculum.py | A small validation script (`set(curriculum topic ids) - set(corpus topic filenames)` and vice versa) | Set-diff is trivial to write and should run in CI or pre-commit, not be a recurring manual chore across 975 topics |

**Key insight:** Everything genuinely custom in this phase — the corpus schema, the gating rules (D-06/D-07), the curation philosophy (D-08/D-09) — is domain-specific and correctly hand-built. The only generic-infrastructure pieces (frontmatter parsing, stdio transport) have mature libraries; don't reimplement those.

## Common Pitfalls

### Pitfall 1: Assuming CORPUS-01 means literally all 975 topics get a hand-written page
**What goes wrong:** REQUIREMENTS.md CORPUS-01 says "Layered topic explanations (L3 wiki pages) exist for all curriculum subjects — one page per topic." Taken literally against `len(CURRICULUM) == 975` (44 subjects), this is a multi-hundred-page writing task, not a single-phase deliverable.
**Why it happens:** The requirement was likely written before the curriculum grew to 975 topics across 44 subjects (STATE.md shows curriculum additions happened after phase context was gathered — CONTEXT.md D-02 itself says "942 after recent additions," and the live count is now 975, i.e. it's still growing).
**How to avoid:** Flag explicitly to the planner: build full infrastructure (directory structure, MCP server, all 5 tools, validation script, migration of existing content) as the phase-complete deliverable, and populate a **pilot set** — recommend one full subject with a small topic count, e.g. `Manipulation`, `Political Systems`, or `Dissent` (these already have real source material via the Happiness in Slavery transcript) — as the content proof-of-concept. Treat "populate remaining ~960 topic pages" as an explicit backlog/todo, not a phase-blocking task. This should be raised as an open question for the planner/discuss-phase, not silently resolved here.
**Warning signs:** A plan that tries to enumerate 975 individual "write topic page X" tasks — this is a sign the scope wasn't caught early.

### Pitfall 2: `.claude/settings.json` vs `.mcp.json` confusion
**What goes wrong:** D-11/D-13 and the code_context section say "register in `.claude/settings.json`," but Claude Code's actual convention for project-scoped MCP servers is a separate `.mcp.json` file at the project root (or a `mcpServers` key inside user/project settings, depending on version). Neither file currently exists in this repo (verified: no `.claude/settings.json`, no `.mcp.json` present).
**Why it happens:** MCP registration file conventions have shifted across Claude Code versions, and CONTEXT.md's language ("a Python script registered in `.claude/settings.json`") may reflect stale terminology from when it was written.
**How to avoid:** Before implementing, verify the current Claude Code version's expected registration file/schema (check `claude --version`, check Claude Code's own docs/changelog, or check for any `.claude/` config precedent in sibling projects). The `mcpServers` JSON block shape is typically:
```json
{
  "mcpServers": {
    "etutor-corpus": {
      "command": "python",
      "args": ["-m", "services.corpus_mcp.server"],
      "cwd": "/absolute/path/to/etutor-server"
    }
  }
}
```

**Warning signs:** Claude Code fails to discover the MCP server, or an existing (undiscovered) MCP config convention in a different location is silently ignored.

### Pitfall 3: Topic ID mismatches between corpus filenames and `Topic.id`
**What goes wrong:** `services/curriculum.py` topic IDs use snake_case (e.g. `exp_bernoulli_flight`, `manipulation`, `political_systems`). If corpus page filenames drift even slightly (extra pluralization, hyphens vs underscores, casing), `get_topic(topic_id)` silently returns nothing and the mismatch isn't caught until runtime.
**Why it happens:** Manual content authoring across hundreds of files without automated validation.
**How to avoid:** Build the validation script (Don't Hand-Roll table) as one of the first infrastructure tasks, not a nice-to-have at the end. Run it in CI/pre-commit so future corpus authoring can't silently drift.
**Warning signs:** `get_topic()` returning "no corpus page" for a topic that a human swears they wrote a page for.

### Pitfall 4: Conflating `docs/wiki/` (existing) with `docs/corpus/wiki/` (new)
**What goes wrong:** The existing `docs/wiki/source-material/` directory and the new `docs/corpus/wiki/sources/` directory look similar enough that a careless migration script or a future contributor could write to the wrong path, or leave stale duplicate files behind in the old location.
**Why it happens:** D-05 says "migration: rename/move existing files" but doesn't specify whether old paths should redirect, 404, or simply cease to exist. `docs/experiment-guides/` (6 existing files, verified: bernoulli-flight.md, bread-baking-science.md, candle-science.md, lemon-battery.md, magnetic-field-mapping.md, pool-chemistry.md) similarly needs a clean move, not a copy, into `docs/corpus/wiki/experiments/` with the new D-07 frontmatter schema added.
**How to avoid:** Treat migration as `git mv` (preserves history) followed by a frontmatter-schema-upgrade edit pass, then delete the old empty directories. Verify existing experiment guides currently have NO frontmatter at all (confirmed: `bernoulli-flight.md` starts directly with `# Bernoulli Effect and Flight — Experiment Guide` and a markdown table, no YAML block) — so migration is not just "move the file," it requires adding the full D-07 frontmatter block (topic_ids, min_age, flagged_dangerous, equipment, safety_notes, level) to every file, derived from each guide's existing "Curriculum topic:" and "Age:" header lines.
**Warning signs:** Two copies of the same content existing at both old and new paths after migration; MCP server finding zero experiments because frontmatter wasn't actually added.

## Code Examples

### Simple keyword search over the in-memory index (per D-14)
```python
# [ASSUMED — illustrative pattern; no external library needed for plain substring search]
def _search_corpus_impl(query: str, subject: str | None = None, level: int | None = None, type_: str | None = None) -> list[dict]:
    query_lower = query.lower()
    results = []
    for bucket_name, bucket in INDEX.items():
        for key, entry in bucket.items():
            meta = entry["metadata"]
            if subject and meta.get("subject") != subject:
                continue
            if level and meta.get("level") != level:
                continue
            if type_ and meta.get("type") != type_:
                continue
            haystack = (entry["content"] + " " + " ".join(meta.get("tags", []) + meta.get("topic_ids", []))).lower()
            if query_lower in haystack:
                results.append({"bucket": bucket_name, "id": key, "metadata": meta})
    return results
```

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal via `topic_id`/`slug` arguments (e.g. `topic_id="../../../../etc/passwd"`) used to construct a filesystem path | Tampering / Information Disclosure | Never build file paths by directly concatenating a tool argument into a `Path()`; instead, always look up the argument as a dict key in the pre-built in-memory index (Architecture Pattern 1) — this makes path traversal structurally impossible since arbitrary strings simply won't be present as dict keys. This is a natural consequence of the recommended architecture, not an extra step, but should be called out explicitly to the planner so no implementation accidentally does `Path(CORPUS_ROOT) / f"{topic_id}.md"` directly from user input. |
| Unbounded `search_corpus` query causing excessive result sets or CPU on a large corpus | Denial of Service (low severity, local process) | Low risk at this corpus's scale (hundreds of files); no special mitigation needed for v1 beyond a sane default result-count cap if it becomes noticeable |
